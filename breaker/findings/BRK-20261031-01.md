## Target
- `backend/app/routers/sessions.py` — `put_capture_image` (lines 309–411)
- `backend/app/middleware/auth.py` — `_verify_and_reserve_phase_a` step 11 (lines 312–337)
- `backend/app/cli.py` — `handle_participant_withdraw` (lines 421–463)

## Expected Safe Behavior (`docs/7_API_Documentation.md` Sections 4.3, 5.2, 7.6; `docs/8_Security_Compliance_Plan.md` T15; `docs/10_Test_Cases.md` TC-API-32)
When a coordinator withdraws a participant (`neogold-admin participant withdraw <code_str>`), the server sets `participant.withdrawn_on`, deletes any stored images for that participant, and marks every session of that participant `status = 'REJECTED'` with `rejected_reason = 'CONSENT_WITHDRAWN'`. Any subsequent upload for that participant — including in-flight `PUT /v1/sessions/{session_id}/captures/{capture_id}/image` requests from a phone that had already uploaded the session manifest before the withdrawal — must be rejected with `422 Unprocessable Entity` (`code: "PARTICIPANT_WITHDRAWN"`) and **must never write the withdrawn participant's image to disk**.

## Actual Behavior (Evidence)
1. `backend/app/middleware/auth.py` step 11 (lines 312–337) only checks `PARTICIPANT_WITHDRAWN` on `PUT /participants/{id}`, `PUT /sessions/{id}` (manifest), and `POST /tsb-measurements`. It does not check `PUT /sessions/{session_id}/captures/{capture_id}/image`.
2. `backend/app/routers/sessions.py` (`put_capture_image`, lines 309–411) checks `session_row.device_id == device_id` and `session_row.status == "COMPLETE"`, but never checks `participant.withdrawn_on is not None` or `session_row.status == "REJECTED"`.
3. Consequently, when a phone uploads a capture JPEG for a session whose participant was withdrawn mid-upload:
   - Lines 364–376 write and `os.replace()` the withdrawn participant's JPEG file onto disk (`{IMAGE_STORE_DIR}/{study_code}/{site_code}/{session_id}/{capture_id}.jpg`), violating consent withdrawal (`T15`, `FR-24`)!
   - When the final capture image of the session arrives (`missing_count == 0`, lines 397–401), `put_capture_image` sets `session_row.status = "COMPLETE"` while `session_row.rejected_reason` remains `"CONSENT_WITHDRAWN"`, violating PostgreSQL constraint `session_status_rejected_reason_check: ((status = 'REJECTED') = (rejected_reason IS NOT NULL))` and crashing with an unhandled `500 IntegrityError` (leaving the withdrawn participant's JPEG file persisted on disk).

## Steps to Reproduce
1. Start the disposable breaker environment and seed synthetic study `SKP-BRK`, test site `SKP01`, an enrolled device, and participant `SKP-0001`.
2. Upload a session manifest `PUT /v1/sessions/{session_id}` with one `has_image=True` capture (`capture_id`). Receive `202 Accepted` (`status: "RECEIVING"`).
3. Withdraw participant `SKP-0001` via `handle_participant_withdraw(db, "SKP-0001")` (which sets `participant.withdrawn_on = today`, `session.status = "REJECTED"`, `session.rejected_reason = "CONSENT_WITHDRAWN"`).
4. Upload the capture JPEG via `PUT /v1/sessions/{session_id}/captures/{capture_id}/image`.
5. Observe that the JPEG file is written to `{IMAGE_STORE_DIR}/SKP-BRK/SKP01/{session_id}/{capture_id}.jpg` and the endpoint crashes with `500 Internal Server Error` (`IntegrityError` on `session_status_rejected_reason_check`) instead of returning `422 PARTICIPANT_WITHDRAWN` with zero files on disk.
