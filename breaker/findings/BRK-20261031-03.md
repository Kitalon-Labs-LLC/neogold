## Target
- `backend/app/cli.py` — `handle_restore_mark` (lines 466–482)

## Expected Safe Behavior (`docs/7_API_Documentation.md` Section 5.4, line 277; `docs/10_Test_Cases.md` TC-SYNC-14)
Per `docs/7_API_Documentation.md` Section 5.4:
> "A coordinator who restores the server from a backup runs `neogold-admin restore mark`, which sets it to the Unix time of the restore, so it always increases even after a second restore. Phones that see a new value re-send **every** item they still hold."

`handle_restore_mark` must guarantee `new_generation = max(int(time.time()), int(study.data_generation) + 1)` so that `data_generation` strictly increases on every invocation, even if `restore mark` is run twice within the same second or if the server clock is slightly behind a prior `data_generation`.

## Actual Behavior (Evidence)
In `backend/app/cli.py` lines 469–473:
```python
now_ts = int(time.time())
studies = db.execute(select(Study)).scalars().all()
for study in studies:
    study.data_generation = now_ts
```
When `handle_restore_mark(db)` is called twice within the same second (or when `study.data_generation >= int(time.time())`), `study.data_generation` is overwritten with `now_ts` rather than `max(now_ts, int(study.data_generation) + 1)`. Because `data_generation` does not increase, phones polling `GET /v1/device` do not detect the second restore and fail to re-upload sessions lost in the second restore.

## Steps to Reproduce
1. Start the disposable breaker environment and seed study `SKP-BRK` (`data_generation = 1`).
2. Call `handle_restore_mark(db)` twice in rapid succession (within the same Unix second, or when `study.data_generation == int(time.time())`).
3. Observe that `study.data_generation` after the second call equals the value after the first call (`gen2 == gen1`) instead of `gen2 > gen1`.
